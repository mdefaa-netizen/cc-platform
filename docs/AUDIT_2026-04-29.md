# CC-Platform Code Audit — 2026-04-29

## Summary

The cc-platform Streamlit app is a 32-day-old codebase (28 commits since the initial scaffold on 2026-03-28) with all 8 spec pages and all 8 spec database tables implemented across both SQLite (local) and Postgres (Supabase) backends, plus 9 additional pages and 8 additional tables for RBAC, the legacy portal, cross-role messaging, audit logging, and staff directories. The codebase is structurally tidy — zero TODO/FIXME debt, zero dead commented-out code, consistent `require_auth(allowed_roles=…)` page gating, and 80-function backend parity between SQLite and Postgres modules — but it is currently blocked from production use by a Supabase pooler authentication failure that lives entirely on Supabase's side (the diagnostic added in commits `21a891f`/`6e8a366`/`923b8fe` confirms the app is sending exactly the credentials the dashboard shows, with the support ticket pending). The audit identified two real silent-failure bugs (the NH event map at `app.py:179` and three of four Settings-page operations at `pages/12_Settings.py`), several RBAC correctness gaps (most notably `pages/11_Feedback.py` which has zero role gating at either layer), two unbuilt planned features (`Fac-XXXXX`/`Hst-XXXXX` auto-credential generation and first-login forced password change), and a handful of credential-in-repo and silent-wrong-DB risks in the standalone scripts. The recommended first-week sequence after Supabase unblocks is: restore visibility on silent failures, close the obvious RBAC gaps after confirming intent with the coordinator, then ship a quick-wins housekeeping bundle.

#### Connection pool config (post-today's three commits)

```python
psycopg2.pool.SimpleConnectionPool(
    minconn=1, maxconn=10,
```

- `get_connection()` checks out a conn from the singleton pool (`_pool`)

### 2B — `utils/database.py` (1,150 lines)

#### Routing logic — bottom of file, lines 1129–1150

```python
try:
    _db_url = None
    try:
        import streamlit as _st
        _db_url = _st.secrets.get("DATABASE_URL")    # 1. st.secrets (preferred)
    except Exception:
        _db_url = None
    if not _db_url:
        _db_url = _os.environ.get("DATABASE_URL")    # 2. os.environ (fallback)
    if _db_url:
        import utils.supabase_db as _pg
        for _name, _obj in _inspect.getmembers(_pg):
            if not _name.startswith("_") and callable(_obj):
                globals()[_name] = _obj              # 3. monkey-patch in
except Exception:
    # 4. anything blows up → SQLite remains active, log warning
```

#### How the SQLite ↔ Postgres decision is made

| Condition | Active backend |
|---|---|
| `st.secrets["DATABASE_URL"]` exists | **Postgres (Supabase)** |
| Else `os.environ["DATABASE_URL"]` exists | **Postgres (Supabase)** |
| Neither exists | **SQLite** (path = `os.environ.get("DB_PATH", "cc_platform.db")`) |

**The decision is made at import-time of `utils.database`, once per process.** There is no runtime toggle, no admin override, no dashboard switch. The presence of `DATABASE_URL` is the single switch.

#### Current production state

| Environment | Backend | Reason |
|---|---|---|
| **Streamlit Cloud** (cc-platform-lwgykmwhsbf954mjqsdgl5) | **Postgres** | `DATABASE_URL` is set in `st.secrets` — confirmed by today's diagnostic showing `[CC_DEBUG_DB] DATABASE_URL source: st.secrets` |
| **Local dev** (no secrets) | **SQLite** (`cc_platform.db`) | `DATABASE_URL` not set; SQLite path defaults to `./cc_platform.db` |

### 🚩 Observations from Step 2

1. **Two parallel auth subsystems**: `users` table (bcrypt, RBAC, email-based — modern) + `portal_access` table (PBKDF2, username-based — legacy). The `hash_password` / `verify_password` functions in `supabase_db.py:25-40` and `database.py:15-30` exist *only* for the legacy `portal_access` path. The bcrypt path lives in `utils/auth.py`. This is a divergence that will surprise future maintainers — comment exists on line 247 (`# Password hashing lives in utils/auth.py (bcrypt).`) but isolated. **Worth either consolidating, or documenting more visibly.**

2. **`init_db()` and `init_all()` both exist** in `supabase_db.py` and do overlapping work (CREATE TABLE blocks with same column lists). The `_schema_initialised` flag prevents double-execution but the duplicated SQL is a maintenance burden — change a column once, must change it twice (`init_all` lines 262–408, plus `init_db` 485+ , plus `init_*()` per-table).

3. **`get_connection()` in SQLite vs. Postgres is semantically different**: SQLite returns a fresh `sqlite3.Connection` (caller closes it); Postgres returns a pooled `psycopg2` connection (caller is supposed to call `_putconn`). Direct callers that bypass the helper functions and use `get_connection()` directly may leak connections on the Postgres side. Worth grepping for direct `get_connection()` callers in pages — flagged for Step 3.

4. **No connection-aliveness check** before checkout: `SimpleConnectionPool` doesn't validate connections; if Supavisor drops one mid-pool, the next checkout will fail at first query rather than at checkout. Switching to `psycopg2.pool.ThreadedConnectionPool` + a `SET application_name='cc-platform'; SELECT 1;` warmup is a small reliability win — flagged for Step 6.

5. **`init_all()` is good, but `app.py` only calls it under `try/except ImportError`**. On a fresh Supabase deploy where `init_all` exists, it's used; on the SQLite path it falls back to splitting init across many functions. Functionally equivalent but the reading order in `app.py` (line 13–15) reads strangely.

### 3A — `get_connection()` direct-caller audit

**4 call sites total**, of which **3 are outside `utils/`**:

| File:Line | Wrapped? | Closes? | SQLite branch | Postgres branch |
|---|---|---|:---:|:---:|
| `app.py:179` (dashboard event map) | Yes — broad `try / except Exception` at app.py:150–252 | Yes (`_map_conn.close()` line 192) | ✅ works | ❌ **silently broken** — `_map_conn.execute(...)` raises `AttributeError` on psycopg2.connection (no `.execute()` at conn level), caught by the broad except, user sees `🗺️ Map could not be rendered: …` |
| `pages/12_Settings.py:127` (CSV export of any table) | **No try/except** — bare path | Yes (`conn.close()` line 129) | ✅ works | ❌ **broken with traceback** — same AttributeError on Postgres |
| `pages/12_Settings.py:147` (Danger Zone DELETE) | **No try/except** | Yes (`conn.commit(); conn.close()`) | ✅ works | ❌ **broken with traceback** — same AttributeError; data not deleted |
| `utils/supabase_db.py` (multiple — `init_all`, `init_db`, `init_*`, `get_user_by_email`, etc.) | n/a — module-internal | All return via `_putconn` helpers or commit-and-leak | n/a | Working — these are inside the helper layer and use the proper pool semantics |

#### Connection-leak risk on Postgres

- **`app.py:179` and `pages/12_Settings.py:127, 147` use `conn.close()` instead of `_putconn(conn)`** — but they fail before reaching `.close()` on Postgres anyway (the `.execute()` call AttributeErrors first). So no leak risk in practice — the leak risk would only materialize *if* someone "fixed" these to use cursors but kept `.close()` instead of `_putconn()`.
- **However**: `psycopg2.pool.SimpleConnectionPool.getconn()` followed by `conn.close()` actually closes the connection AND breaks the pool's accounting — it doesn't throw, it just leaks a slot. So if any of these paths gets fixed for Postgres without switching to `_putconn`, we'd silently bleed pool slots until `maxconn=10` is exhausted.

#### Bonus broken-on-Postgres path

- `pages/12_Settings.py:112-115` — **"Download Backup"** button reads from `DB_PATH`. On Postgres, `DB_PATH = "supabase"` (sentinel set in `utils/supabase_db.py:42`), so `open("supabase", "rb")` raises `FileNotFoundError`. Not wrapped. User sees a traceback.

## Step 4 — Authentication and RBAC

### 4A — `utils/auth.py` (206 lines, single module)

#### What it does

Centralizes all auth: bcrypt hashing, user CRUD dispatch (SQLite/Postgres), `require_auth()` page guard, sidebar block, bootstrap coordinator seeding.

#### How user accounts are stored

`users` table (line `383` of `supabase_db.py` / created in `init_users()` of `database.py`):

```sql
users (
    id INTEGER/SERIAL PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL CHECK (role IN
        ('coordinator','facilitator','host','cdfa_staff','nhh_staff')),
    full_name TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_active INTEGER NOT NULL DEFAULT 1
)
```

CHECK constraint on role enforces the 5-role universe at the DB level. Indexes on `email` and `role`.

#### Password hashing — bcrypt ✅

```python
bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode("utf-8")
```

- **Rounds: hardcoded `12`** at `utils/auth.py:58`. Not configurable via env, secrets, or constant.
- 12 is a sane default (~250ms per hash on modern hardware), but no upgrade path — to bump to 13/14 later means a code change and forces all users to keep their old-rounds hashes until they reset.
- `verify_password` is a thin wrapper over `bcrypt.checkpw`, returns `False` on any exception (no traceback leakage).

#### Session — Streamlit `session_state`, not a cookie

| Aspect | Details |
|---|---|
| **Mechanism** | `st.session_state` — server-side, scoped per-browser-tab Streamlit session, NOT a real cookie. Lost on app restart, browser tab close, or full reload. |
| **Keys set on login** | `authenticated`, `user_id`, `user_email`, `user_role`, `user_label`, `user_full_name`, `_login_at`, `_login_attempts` (reset to 0) |
| **Expiry** | `SESSION_TIMEOUT_SECONDS = 3600` (1 hour, hardcoded `utils/auth.py:34`) |
| **Expiry check** | On every page load via `require_auth()`: `if time.time() - _login_at > 3600: clear + redirect to login` |
| **Logout** | `render_sidebar_user()` "Sign Out" button calls `st.session_state.clear()` then `switch_page` |
| **Cross-tab** | Each browser tab has its own session_state — opening a 2nd tab to `/` while the first tab is signed-in starts as **unauthenticated** in tab 2 |

⚠️ **No persistent cookie/JWT** — every browser refresh that loses the Streamlit websocket also kills the session. Users have to re-login frequently, especially after Streamlit Cloud cold starts.

#### Rate limiting on login — IT EXISTS, but at the wrong layer

In `pages/0_Login.py:32-33, 55-57, 91-117`:

```python
_MAX_LOGIN_ATTEMPTS = 5
_LOCKOUT_SECONDS    = 300   # 5 minutes
```

After 5 failures within one Streamlit session: lockout for 5 minutes, sign-in button disabled.

🚨 **Critical caveat — this is per-`session_state`, not per-IP/email**:
- The `_login_attempts` counter and `_lockout_until` timestamp live in `st.session_state`
- A scripted attacker who **rotates browser tabs** (or simply discards the Streamlit session cookie) gets a fresh counter every time
- There is **no server-side throttle**, no IP-based rate limit, no per-email lockout
- Effectively, the lockout protects an honest user who fat-fingers their password — it does not protect against a credential-stuffing attack

#### Backend dispatch (`_backend()`, lines 40–52)

Same logic as `utils.database`'s routing — checks `st.secrets["DATABASE_URL"]` first, then `os.environ["DATABASE_URL"]`, falls back to SQLite. Returns the live module reference, used by `get_user_by_email`, `create_user`, `list_users`, `update_user_role`, `set_user_active`, `reset_user_password`.

| Function | Purpose |
|---|---|
| `hash_password`, `verify_password` | bcrypt wrappers |
| `generate_password(length=16)` | `secrets.choice` over `string.ascii_letters + string.digits` (alphanumeric only) |

### 🚩 Observations from Step 4

1. **Auto-credential generation for facilitators/hosts is unbuilt** — and there's no "first login" force-change flow either. Two distinct features that match project memory but don't exist in code. 3. **No persistent session cookie** — Streamlit `session_state` is in-memory and tab-scoped. 4. **bcrypt rounds is hardcoded to 12, no upgrade path** — when 13 becomes the new default, all existing hashes stay at 12 silently. A `_BCRYPT_ROUNDS = int(os.environ.get("BCRYPT_ROUNDS", "12"))` plus a re-hash-on-login mechanism would future-proof this. Low priority for now.
5. **Facilitator → Reports access mismatch** — facilitators are excluded from `pages/10_Reports.py` despite the spec saying they should have access. Either fix the page (`allowed_roles=["coordinator", "facilitator", "cdfa_staff", "nhh_staff"]`) or update the spec.
6. **Host → Facilitators access mismatch** — hosts are excluded from `pages/4_Facilitators.py` despite the spec saying they should see their associated facilitator. Either include `host` in `allowed_roles` and add row-scoping (only show their event's facilitator), or update the spec.
7. **`pages/11_Feedback.py` has zero role gating, page or UI level** — any authenticated user can submit feedback for any event. Combined with Step 3 finding #5 about no `allowed_roles=`. Two flags pointing at the same page.
8. **No "read-only role" helper** — UI guards spell out `if _is_coord:` everywhere. Easy to forget on new pages. A `can_write(role)` helper would centralize.
9. **NHH/CDFA staff cannot see their own org's directory page** (`5_NHH_Colleagues`, `6_CDFA_Colleagues` are coordinator-only). Probably an oversight — confirm intent.
10. **Bootstrap coordinator runs from BOTH `app.py:31` and `pages/0_Login.py:49`** — redundant but harmless; both gated by `if not users:`.
